# Career Playability And Engine Roadmap

Date: 2026-06-25
Baseline: Phase 61 complete; Claude Code full-project analysis reviewed.
Scope: operational phase roadmap from Phase 62 onward.

## Goal

Turn the current deterministic football simulation into a playable career loop
that the user can feel, understand, and continue through the web app.

This roadmap has three goals, in priority order:

1. Make the game more fun and more legible for the manager.
2. Keep the engine deterministic, testable, and owned by deep Modules.
3. Keep the web app as an Adapter over structured read models, not a second
   game engine.

The roadmap intentionally delays large new pillars such as full finances,
promotion pyramids, staff, facilities, and narrative media until the existing
match, career, player, and web loop can actually be played end to end.

## Supersession Note

From Phase 62 onward, this roadmap supersedes the previous linear web-only
ordering in `docs/roadmaps/CAREER_WEB_SECTION_ROADMAP.md`.

The web roadmap remains valid as the section-quality standard, especially for
browser QA, accessibility, and section completion. Its old recommendation to do
Inbox/Posta immediately after Phase 61 is no longer the preferred order.

The new order is:

1. harden the engine contract and deterministic gates;
2. create one canonical career advancement Module;
3. make player state react to matches;
4. connect real matchday to the web;
5. then build Inbox/Posta around real attention events.

## Non-Negotiable Constraints

- User fun, football credibility, readability, and emergent stories come before
  making reports green.
- Engine Modules must not import React, storage implementations, browser APIs,
  CLI, content generation, or i18n.
- Web code must not duplicate engine rules.
- `@game/ui` stays framework-free and language-agnostic.
- No CLI prose parsing for web screens.
- No hidden manager decisions. Auto actions must be explicit manager-triggered
  helpers.
- No decorative web section before the underlying decision or state exists.
- No new hardcoded visible labels. User-facing text must go through i18n.
- Engine and domain code emit structured facts only. Narrative wording,
  commentary, news, press text, and future LLM-generated corpus selection must
  live outside the engine behind a content/presentation/narrator seam.
- LLM usage is authoring-time only: no runtime LLM calls, no build-time API
  calls in normal project commands, and no gameplay truth generated by an LLM.
- Use Node `24.16.0`; run `nvm use 24` before project commands in a fresh
  shell.
- Web/UI phases require Playwright screenshot QA for desktop and narrow
  viewports, plus keyboard/focus notes.

## Phase Entry Gate

Every future phase must answer these questions before step docs are written:

1. What user-facing decision, tension, or story does this phase improve?
2. Which domain or engine state backs it?
3. Which Module owns the rule?
4. Which Interface should callers use?
5. Which Adapter consumes it first: CLI, web, or both?
6. What deterministic test or golden evidence protects it?
7. What is explicitly out of scope?
8. What would count as dead code in this phase?

If any answer is weak, the first step of the phase must be an audit/spec step.

## Phase Exit Gate

A phase is complete only when:

- the user-facing reason for the change is documented;
- the Module ownership is clear;
- `pnpm check` passes unless the phase explicitly documents a blocker;
- relevant deterministic tests exist for engine or read-model logic;
- web-visible work has Playwright screenshots and accessibility notes;
- no known dead code, unused helper, or obsolete Adapter remains undocumented;
- the phase report recommends exactly one next phase.

### Phase 73 - Inbox/Posta Decision Center And Career Attention Workflow

Primary dependency: Phase 72 career session cadence and command feedback.

Purpose:

- Turn Inbox/Posta into the manager's structured decision center and make
  `Continue` evaluate canonical game days until the first meaningful attention
  date.

User-facing reason:

- "Continua" should stop only when the manager needs to know or decide
  something. Posta must explain why time stopped and expose one useful football
  action without becoming a bureaucratic mail client.

Locked product contract:

- Attention levels are exactly `blocking`, `important`, and `informational`.
- `Continue` stops only for blocking or important attention. Informational
  messages are delivered without interrupting advancement.
- Days are evaluated deterministically; every message on the first attention
  date is delivered together and the highest-priority message is selected.
- Matchday is one blocking message on the fixture date. Missing lineup, bench,
  or tactic are details of that message, not a separate preparation stop.
- Opening marks read; important messages acknowledge on open; blocking
  messages resolve only when their structured requirement changes.
- Current-season messages persist with the career and clear on new-season
  transition. No historical archive is introduced.
- Standard screens keep a compact left Posta rail. The selected Posta outlet
  is a dense two-column list/detail workspace, collapsing to list then detail
  on narrow screens.
- Calendar movement is presented with a short day-by-day transition that
  accelerates after seven days, caps near two seconds, and respects reduced
  motion. It is not fake engine progress.

Initial supported message policy:

- blocking: selected-club matchday;
- important: supported season-rollover summary;
- informational: played-fixture result plus ordinary structured player-state
  consequences;
- exceptional player consequences stay informational until the engine owns an
  explicit severity fact.

Ordered implementation:

1. audit current attention, Posta, persistence, and deletion targets;
2. define canonical attention levels and durable message lifecycle;
3. implement daily advancement, same-date batching, and stop policy;
4. persist current-season Inbox state and reset it at season transition;
5. expose lifecycle use cases through the existing career runtime/session;
6. add UI read models, Posta route, and screen state;
7. build the Football Manager-style rail, list, and detail workspace;
