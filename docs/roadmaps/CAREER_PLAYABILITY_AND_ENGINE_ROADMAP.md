## Goal

Turn the current deterministic football simulation into a playable career loop
that the user can feel, understand, and continue through the web app.

This roadmap has three goals, in priority order:

1. Make the game more fun and more legible for the manager.
2. Keep the engine deterministic, testable, and owned by deep Modules.
3. Keep the web app as an Adapter over structured read models, not a second
   game engine.

The roadmap intentionally delays large new pillars such as full finances,
promotion pyramids, staff, facilities, and narrative media until the existing
match, career, player, and web loop can actually be played end to end.

## Supersession Note

From Phase 62 onward, this roadmap supersedes the previous linear web-only
ordering in `docs/roadmaps/CAREER_WEB_SECTION_ROADMAP.md`.

The web roadmap remains valid as the section-quality standard, especially for
browser QA, accessibility, and section completion. Its old recommendation to do
Inbox/Posta immediately after Phase 61 is no longer the preferred order.

The new order is:

1. harden the engine contract and deterministic gates;
2. create one canonical career advancement Module;
3. make player state react to matches;
4. connect real matchday to the web;
5. then build Inbox/Posta around real attention events.

## Non-Negotiable Constraints

- User fun, football credibility, readability, and emergent stories come before
  making reports green.
- Engine Modules must not import React, storage implementations, browser APIs,
  CLI, content generation, or i18n.
- Web code must not duplicate engine rules.
- `@game/ui` stays framework-free and language-agnostic.
- No CLI prose parsing for web screens.
- No hidden manager decisions. Auto actions must be explicit manager-triggered
  helpers.
- No decorative web section before the underlying decision or state exists.
- No new hardcoded visible labels. User-facing text must go through i18n.
- Engine and domain code emit structured facts only. Narrative wording,
  commentary, news, press text, and future LLM-generated corpus selection must
  live outside the engine behind a content/presentation/narrator seam.
- LLM usage is authoring-time only: no runtime LLM calls, no build-time API
  calls in normal project commands, and no gameplay truth generated by an LLM.
- Use Node `24.16.0`; run `nvm use 24` before project commands in a fresh
  shell.
- Web/UI phases require Playwright screenshot QA for desktop and narrow
  viewports, plus keyboard/focus notes.

## Phase Entry Gate

Every future phase must answer these questions before step docs are written:

1. What user-facing decision, tension, or story does this phase improve?
2. Which domain or engine state backs it?
3. Which Module owns the rule?
4. Which Interface should callers use?
5. Which Adapter consumes it first: CLI, web, or both?
6. What deterministic test or golden evidence protects it?
7. What is explicitly out of scope?
8. What would count as dead code in this phase?

If any answer is weak, the first step of the phase must be an audit/spec step.

## Phase Exit Gate

A phase is complete only when:

- the user-facing reason for the change is documented;
- the Module ownership is clear;
- `pnpm check` passes unless the phase explicitly documents a blocker;
- relevant deterministic tests exist for engine or read-model logic;
- web-visible work has Playwright screenshots and accessibility notes;
- no known dead code, unused helper, or obsolete Adapter remains undocumented;
- the phase report recommends exactly one next phase.

### Phase 73 - Inbox/Posta Decision Center And Career Attention Workflow

Primary dependency: Phase 72 career session cadence and command feedback.

Purpose:

- Turn Inbox/Posta into the manager's structured decision center and make
  `Continue` evaluate canonical game days until the first meaningful attention
  date.

User-facing reason:

- "Continua" should stop only when the manager needs to know or decide
  something. Posta must explain why time stopped and expose one useful football
  action without becoming a bureaucratic mail client.

Locked product contract:

- Attention levels are exactly `blocking`, `important`, and `informational`.
- `Continue` stops only for blocking or important attention. Informational
  messages are delivered without interrupting advancement.
- Days are evaluated deterministically; every message on the first attention
  date is delivered together and the highest-priority message is selected.
- Matchday is one blocking message on the fixture date. Missing lineup, bench,
  or tactic are details of that message, not a separate preparation stop.
- Opening marks read; important messages acknowledge on open; blocking
  messages resolve only when their structured requirement changes.
- Current-season messages persist with the career and clear on new-season
  transition. No historical archive is introduced.
- Standard screens keep a compact left Posta rail. The selected Posta outlet
  is a dense two-column list/detail workspace, collapsing to list then detail

### Phase 81 - Phase-Aware Tactical Shape And Manager Decision Engine

Primary dependency: Phase 80C Done with bounded market/race evidence and the
shared deterministic career/match execution seams intact.

Status:

- Planned under an accepted design contract. Do not start before Phase 80C
  closes.

Purpose:

- Make formation shape, role suitability, opponent matchup, tactical
  instructions, and live manager changes materially affect deterministic match
  outcomes without turning the game into a Football Manager clone or a
  22-agent simulation.

Minimum useful scope:

- reproducible extreme-shape baselines led by the equal-quality `3-1-6` versus
  `4-4-2` case, where the current four-department means are identical;
- typed formation line, channel, side, canonical role, and suitability facts
  carried through the match Adapter instead of collapsed into four open-string
  role keys;
- separate concepts for player quality, intrinsic shape capacity, and
  relational opponent matchup;
- configured diminishing returns and continuity/coverage effects, never
  arbitrary named-formation penalties;
- phase-aware buildup, progression, creation, box occupation, defensive
  protection, transition, and width routes;
- explicit semantics for mentality, directness, pressing, width, risk, and
  tempo through one pre-match/live/AI/batch decision seam;
- suitability-based coordination effects with an explicit guard against
  double-penalising the destination-role attribute weighting already present;
- a pre-coefficient quality-versus-structure hierarchy: coherent shape wins
  materially at equal quality, severe incoherence may overturn only modest
  quality gaps, and a generated First Division title contender remains the
  aggregate favourite over a generated Third Division mid-table side under the
  frozen extreme-shape handicap;
- causal actor selection before outcome resolution and structured explanation
  facts usable by UI and diagnostics;
- deterministic AI whole-XI/tactical evaluation against the same model;
- non-vacuous tactical diagnostics and metamorphic invariants;
- one final checkpointed `50 x 20` in Step 12 with `50` stable shards,
  exactly `7` workers, checkpoint reuse, and deterministic replay.

Clean-code contract:

- New and modified names must expose football meaning; no generic
  `utils`, `helpers`, `manager`, `processor`, or boolean-flag orchestration
  modules.
- A step must remove obsolete local collapse/fallback paths once their typed
  replacement is live.
- If implementation exposes dead or structurally unclear code inside the
  active responsibility, the step expands its Expected Files before editing
  and completes the local refactor with tests. Unrelated cleanup is documented
  for a later step rather than mixed into the current change.
- No compatibility branch for beta saves; incompatible saves use the canonical
  reset path.

What must not happen:

- No imitation of proprietary Football Manager internals or unsupported claim
  about its algorithm.
- No 22 autonomous agents, pass-by-pass physics model, named-formation lookup
  table, random upset boost, web-owned match rule, or duplicated AI formula.
- No shape multiplier folded into `TeamStrength`, no persisted derived shape
  profile, and no public stringly typed tactical contract.

Definition of Done:

- Equal-quality extreme formations are no longer mechanically identical, while
  coherent unusual shapes remain viable when their qualities and opponent
  matchup support them.
- Pre-match and live changes use the same deterministic model and expose
  bounded qualitative consequences.
- Focused unit, metamorphic, persistence, browser, dependency, and repository
  gates pass with positive observations.
- Step 12 completes and replays the final `50 x 20`, then hands its truthful
  evidence to Phase 79 Step 14 without claiming that separate release gate.

### Phase 84 - Narrative Content Factory And Corpus Foundation

Primary dependency: a playable matchday loop, durable structured match/world
events, and at least one surface where narrative variety would improve user
retention.

Purpose:

- Create the authoring-time pipeline that will later let the project use LLMs
  to produce richer commentary, news, press, and event text without putting an
  LLM inside the game.

User-facing reason:

- The game should feel less repetitive and more alive while staying offline,
  deterministic, localized, and credible.

Minimum useful scope:

- define the narrative template schema:
  - stable `templateId`;
  - `corpusVersion`;
  - structured event type;
  - slots;
  - conditions/tags;
  - supported language fields or localization keys;
  - validation errors;
- define where authoring prompts live and how they are versioned;
- define what raw LLM output is allowed to be kept, ignored, or committed;
- create a tiny curated corpus for one narrow surface, preferably match ticker
  commentary or post-match summary;
- add a deterministic narrator Adapter that maps structured facts to templates
  without importing engine internals;
- prove that engine/domain still emit only facts and do not select prose;
- document human review and localization QA expectations.

What must not happen:

- No runtime LLM.
- No LLM calls in `pnpm build`, `pnpm check`, tests, or release scripts.
- No LLM-generated gameplay numbers or decisions.
- No conference press system before the core matchday and Inbox loops are
  working.
- No broad corpus generation before the schema, validator, and review process
  exist.
- No rendered narrative prose stored in engine/domain state.

Definition of Done:

- The project has a content-factory seam ready for future LLM-assisted content.
- The first corpus is tiny, curated, schema-validated, deterministic, and
  non-essential to gameplay correctness.
- Engine facts can be rendered with more variety without changing engine
  behavior.
