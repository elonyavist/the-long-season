# Career Playability And Engine Roadmap

Date: 2026-06-25
Baseline: Phase 61 complete; Claude Code full-project analysis reviewed.
Scope: operational phase roadmap from Phase 62 onward.

## Goal

Turn the current deterministic football simulation into a playable career loop
that the user can feel, understand, and continue through the web app.

This roadmap has three goals, in priority order:

1. Make the game more fun and more legible for the manager.
2. Keep the engine deterministic, testable, and owned by deep Modules.
3. Keep the web app as an Adapter over structured read models, not a second
   game engine.

The roadmap intentionally delays large new pillars such as full finances,
promotion pyramids, staff, facilities, and narrative media until the existing
match, career, player, and web loop can actually be played end to end.

## Supersession Note

From Phase 62 onward, this roadmap supersedes the previous linear web-only
ordering in `docs/roadmaps/CAREER_WEB_SECTION_ROADMAP.md`.

The web roadmap remains valid as the section-quality standard, especially for
browser QA, accessibility, and section completion. Its old recommendation to do
Inbox/Posta immediately after Phase 61 is no longer the preferred order.

The new order is:

1. harden the engine contract and deterministic gates;
2. create one canonical career advancement Module;
3. make player state react to matches;
4. connect real matchday to the web;
5. then build Inbox/Posta around real attention events.

## Non-Negotiable Constraints

- User fun, football credibility, readability, and emergent stories come before
  making reports green.
- Engine Modules must not import React, storage implementations, browser APIs,
  CLI, content generation, or i18n.
- Web code must not duplicate engine rules.
- `@game/ui` stays framework-free and language-agnostic.
- No CLI prose parsing for web screens.
- No hidden manager decisions. Auto actions must be explicit manager-triggered
  helpers.
- No decorative web section before the underlying decision or state exists.
- No new hardcoded visible labels. User-facing text must go through i18n.
- Engine and domain code emit structured facts only. Narrative wording,
  commentary, news, press text, and future LLM-generated corpus selection must
  live outside the engine behind a content/presentation/narrator seam.
- LLM usage is authoring-time only: no runtime LLM calls, no build-time API
  calls in normal project commands, and no gameplay truth generated by an LLM.
- Use Node `24.16.0`; run `nvm use 24` before project commands in a fresh
  shell.
- Web/UI phases require Playwright screenshot QA for desktop and narrow
  viewports, plus keyboard/focus notes.

## Phase Entry Gate

Every future phase must answer these questions before step docs are written:

1. What user-facing decision, tension, or story does this phase improve?
2. Which domain or engine state backs it?
3. Which Module owns the rule?
4. Which Interface should callers use?
5. Which Adapter consumes it first: CLI, web, or both?
6. What deterministic test or golden evidence protects it?
7. What is explicitly out of scope?
8. What would count as dead code in this phase?

If any answer is weak, the first step of the phase must be an audit/spec step.

## Phase Exit Gate

A phase is complete only when:

- the user-facing reason for the change is documented;
- the Module ownership is clear;
- `pnpm check` passes unless the phase explicitly documents a blocker;
- relevant deterministic tests exist for engine or read-model logic;
- web-visible work has Playwright screenshots and accessibility notes;
- no known dead code, unused helper, or obsolete Adapter remains undocumented;
- the phase report recommends exactly one next phase.

- No third advancement path left behind.

Definition of Done:

- There is one canonical career advancement Module.
- CLI paths call that Module instead of recreating the order locally.
- A future web Adapter can advance a season without knowing the internal order.

### Phase 64 - Match Consequences And Player State Reactivity

- expose structured consequence summaries, not rendered prose;

- No team talks yet.

- No automatic user rotation advice.
- No tuning solely to make long-run reports greener.

Definition of Done:

- After a fixture, at least some selected-club players can have changed
  fitness, form, or morale for football-plausible reasons.
- The consequences are visible through structured data and can later feed web
  read models.

### Phase 65 - Web Matchday Playable Slice

- No half-time team talk.
- No opponent board.
- No fake matchday data if engine data is missing.

Definition of Done:

- A user can reach matchday, play the fixture, and return to a changed career
  dashboard without using the CLI.

Current progress:

### Phase 67 - Web Matchday Flow Simplification And Half-Time Tactical Decisions

Primary dependency: Phase 66 interactive matchday flow.

Purpose:

- Simplify the web matchday path before persistence: one primary action per
  screen, no dead available buttons, no dashboard bounce after preparation, and
  a useful half-time tactical workspace.

User-facing reason:

- The match is the emotional payoff. The user should not fight duplicate
  buttons, inert actions, or bureaucratic routing to reach the important
  football decisions.

Minimum useful scope:

- audit current buttons, click counts, dead actions, duplicates, and shell noise;
- make shell actions contextual so matchday hides Inbox/Posta and ambiguous
  global Continue;
- keep future nav sections visible but not available-looking;
- remove dashboard actions that have no useful handler;
- make dashboard expose one primary next action;

  match" action;
- keep explicit pre-match "Start match";
- make full-time use one final "Continue";
- add half-time selected-club tactical decisions: substitutions, full formation
  change, and tactical-board position/role changes before the second half;
- prove the simplified flow with Playwright desktop/narrow screenshots and
  click-count evidence.

What must not happen:

- No persistence/localStorage/save adapter.
- No new career storage model.
- No team talks.
- No opponent tactical board.
- No live minute-by-minute replay.
- No hidden automatic selected-club decisions.
- No decorative controls that are not backed by structured behavior.

Definition of Done:

- The accepted cold path is reduced to useful clicks:
  `Prepare match -> Auto/manual -> tactic -> Save and go to match -> Start
  match -> half-time decisions -> Start second half -> Continue`.
- Dashboard has one primary next action and no dead available actions.
- Matchday hides Inbox/Posta and unrelated global Continue.
- Half-time allows substitutions and full tactical-board changes for the
  selected club.
- Playwright proves no horizontal overflow, no duplicated meaningless CTA, and
  accessible primary actions.

Result:

  dashboard, preparation, pre-match, half-time, and full-time state. Matchday
  hides Inbox/Posta and the global Continue, preparation saves directly into
  pre-match, full time returns through one `Continue`, and half-time uses the
  shared tactical-board plus fixed bench board for selected-club formation,
  lineup, role, position, and bench decisions.
- Browser QA passed on desktop and narrow viewports with a maximum of 8 clicks
  from new career to dashboard after full time, no horizontal overflow, no
  stale post-match attention, and keyboard-focusable primary actions.
- Residual risk: web career state is still in-memory and disappears on refresh.
  Superseded conclusion: persistence originally looked like the next risk, but

  unless explicitly scoped.
- No fake numbers that do not affect decisions.
- No finance screen full of decorative accounting lines.

Definition of Done:

- At least one manager decision is constrained by money in a visible,
  understandable way.

### Phase 75 - Promotion Pyramid And La Scalata Foundation

Primary dependency: Phase 63 canonical season advancement and enough persistence
to survive multiple seasons.

Purpose:

- Start turning the one-league simulation into the actual "La Scalata" promise.

User-facing reason:

- The identity of the game is bringing a lower-division club upward. That cannot
  wait forever, but it must sit on a stable loop.

Minimum useful scope:

- spec the first multi-division country model;
- promotion/relegation rules for the minimal supported pyramid;
- rollover that moves clubs between competitions deterministically;
- fixture/calendar regeneration after movement;
- table/history persistence across divisions;
- smoke tests for multi-season promotion/relegation.

What must not happen:

- No continental cups.
- No all-five-nation full pyramid in the first slice.
- No real-club licensing or real names.
- No economy/facility requirements unless Phase 73 already supports them.

Definition of Done:

- A deterministic career can move clubs between divisions and preserve coherent
  history.

### Phase 76 - Youth, Staff, Facilities, And Archive Expansion Plan

Primary dependency: Phases 69, 70, 74, and 75.

Purpose:

- Re-plan the remaining large systems after the playable loop, money pressure,

User-facing reason:

Minimum useful scope:

- update roadmaps and create the next phase docs.

- No staff/facility screen with names and no effects.

Definition of Done:

### Phase 77 - Narrative Content Factory And Corpus Foundation

Primary dependency: a playable matchday loop, durable structured match/world
events, and at least one surface where narrative variety would improve user
retention.

Purpose:

- Create the authoring-time pipeline that will later let the project use LLMs
  to produce richer commentary, news, press, and event text without putting an
  LLM inside the game.

User-facing reason:

- The game should feel less repetitive and more alive while staying offline,
  deterministic, localized, and credible.

Minimum useful scope:

- define the narrative template schema:
  - stable `templateId`;
  - `corpusVersion`;
  - structured event type;
  - slots;
  - conditions/tags;
  - supported language fields or localization keys;
  - validation errors;
- define where authoring prompts live and how they are versioned;
- define what raw LLM output is allowed to be kept, ignored, or committed;
- create a tiny curated corpus for one narrow surface, preferably match ticker
  commentary or post-match summary;
- add a deterministic narrator Adapter that maps structured facts to templates
  without importing engine internals;
- prove that engine/domain still emit only facts and do not select prose;
- document human review and localization QA expectations.

What must not happen:

- No runtime LLM.
- No LLM calls in `pnpm build`, `pnpm check`, tests, or release scripts.
- No LLM-generated gameplay numbers or decisions.
- No conference press system before the core matchday and Inbox loops are
  working.
- No broad corpus generation before the schema, validator, and review process
  exist.
- No rendered narrative prose stored in engine/domain state.

Definition of Done:

- The project has a content-factory seam ready for future LLM-assisted content.
- The first corpus is tiny, curated, schema-validated, deterministic, and
  non-essential to gameplay correctness.
- Engine facts can be rendered with more variety without changing engine
  behavior.
